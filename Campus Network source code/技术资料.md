## 1. Portal 认证接口完整 API 文档

### 1.2 接口总表

| #   | 方法与路径                                | 作用                       | 参数编码                                                       | 响应包体                                     |
|:--- |:---------------------------------- |:------------------- |:------------------------------------------------------- |:------------------------------------- |
| 1   | `GET :803/eportal/portal/page/loadConfig` | 取页面配置（门户能力清单） | `wlan_user_ip`/`wlan_ac_ip` 用 **URL 编码的 base64**，其余明文 | `dr1001({"code":1,"msg":…,"data":{…}})`      |
| 2   | `GET :803/eportal/portal/online_list`     | 查在线用户                 | 值**先 base64 再 XOR**                                         | `dr1002({"result":0,…,"list":[],"total":0})` |
| 3   | `GET :803/eportal/portal/login`           | **登录（核心）**           | 值**明文再 XOR**                                               | `dr1003({"result":1,…})`                     |
| 4   | `GET :801/eportal/?c=Portal&a=login`      | 旧接口（回退用）           | URL 编码                                                       | 已废：HTML 错误页（早年实测 HTTP 500）       |

**三条编码规则互不相同，别混用。** 门户 JS `a41.js` 的加密闸门**只把 `page/loadConfig` 排除在外**，
所以其余 `eportal/portal/*` 都会被 `enc_pwd` 处理；而 `online_list` 传进去的本来就是 base64 字符串，
于是变成「base64 再 XOR」。

### 1.3 接口详解

#### ① loadConfig：取页面配置

```
GET http://10.0.10.252:803/eportal/portal/page/loadConfig
      ?callback=dr1001
      &program_index=              ← 首次为空，响应会回填
      &page_index=                 ← 同上
      &wlan_vlan_id=0
      &wlan_user_ip=MTAuMjAuMzAuNDA%3D       ← base64("10.20.30.40")，URL 编码
      &wlan_user_ipv6=                        ← 始终为空
      &wlan_user_ssid=
      &wlan_user_areaid=
      &wlan_ac_ip=MTAuMTI4LjI1NS4xMjk%3D      ← base64("10.128.255.129")
      &wlan_ap_mac=000000000000
      &gw_id=000000000000
      &jsVersion=4.X
```

响应（实测 4368 字节）：

```json
dr1001({"code":1,"msg":"加载页面设置信息成功!",
        "data":{"program_index":"vDRn3i1789461695",
                "page_index":"wfIsOK1789465453",
                "page_name":"gzlg1", ... }})
```

- `program_index` / `page_index` 由服务端下发，**登录和在线列表请求里要带上**。
- 响应里的 `data` 是一份**完整门户能力清单**（80+ 字段），见 [§5.4](#54-loadconfig-返回的门户能力清单)。

#### ② online_list：在线列表

```
GET http://10.0.10.252:803/eportal/portal/online_list
      ?callback=dr1002
      &user_account=             ← 空
      &user_password=            ← 空
      &wlan_user_mac=...         ← 先 base64 再 XOR
      &wlan_user_ip=...          ← 先 base64 再 XOR
      &wlan_user_ipv6=
      &jsVersion=4.X
      &uuid=
      &login_method=1
      &wlan_ac_ip=...            ← 先 base64 再 XOR
      &program_index=...
      &page_index=...
      &encrypt=1&v=<4位随机>&lang=zh
```

响应：`dr1002({"result":0,"msg":"获取用户在线信息数据为空！","list":[],"total":0})`

#### ③ portal/login：登录（核心）

```
GET http://10.0.10.252:803/eportal/portal/login
      ?callback=dr1003
      &login_method=1
      &is_base64encode=0
      &user_account=<XOR>,0,<学号>
      &user_password=<XOR>
      &wlan_user_ip=<XOR>              ← 明文 IP，不是 base64
      &wlan_user_ipv6=
      &wlan_user_mac=<XOR>             ← 去横线、大写
      &wlan_vlan_id=0
      &wlan_ac_ip=<XOR>
      &wlan_ac_name=

      &jsVersion=4.5.1
      &uuid=

      &terminal_type=1
      &business_type=1
      &enable_r3=0
      &mac_type=0
      &lang=zh-cn
      &user_agent=<XOR>                ← 整个 UA 串也被混淆
      &encrypt=1&v=<4位随机>&lang=zh   ← 尾部三个不混淆
```

成功：`dr1003({"result":1,"msg":"Portal协议认证成功！"})`

#### ④ 旧接口（回退）

GET http://10.0.10.252:801/eportal/?c=Portal&a=login&callback=dr1003&login_method=1

      &wlan_user_ip=...&wlan_user_mac=...&wlan_ac_ip=...&wlan_ac_name=

这也是历史上「登不上」的真正根因：旧脚本打的是这个接口。

### 1.4 参数混淆规则（重点）

```
编码：每个字符 XOR key → 转 2 位小写十六进制
解码：每 2 位 hex 还原 1 字节 → XOR key → 字符
```

**key 不是常量，由「客户端 IP 字符串」推导**：

```
key = IP 字符串每个字符的 ASCII 码 逐位异或
```

来自门户自带 JS `a41.js` 的 `util.getkey(term.ip)`：

```javascript
getkey: function (ip) {
    var ret = 0;
    for (var i = 0; i < ip.length; i++) ret ^= ip.charCodeAt(i);
    return ret;
}
```

**实测验证（三种客户端网段各推导一次；下表 IP 为合成示例）：**

| 客户端 IP（合成） | 推导出的 key | 该 IP 的混淆值 | 解码结果 |
|:---------- |:----- |:------- |:---- |
| `10.20.30.40`     | `0x2A`       | `4e581b1a1a19` | `dr1003` |
| `10.20.30.41`     | `0x2B`       | `4f591a1b1b19` | `dr1002` |
| `10.20.30.42`     | `0x28`       | `4c5a1918181b` | `dr1003` |

> ⚠️ **上表三个 IP 都是合成示例**（真实抓包已按隐私要求从仓库移除）。
> 它仍是一张“IP → key → 密文”的完整对照，可自行用 `Get-DrappallKey` / `ConvertTo-DrappallValue` 复核。

> ⚠️ **写死某个 key 会被门户拒绝**：key 不对时返回
> `dr0001({"code":403,"result":0,"msg":"请求参数包含非法内容，请检查后重试",...})`。
> 这也是「有线能登、换 WiFi 就登不上」的原因。
> 注：这条来自**项目实测**（本机把 key 写死为 `0x20` 时门户回的就是它）：
> **这条响应来自项目实测**（不在这 5 份抓包里：当时 key 都是算对的）。

另有一条独立规则：**`callback` 参数本身也参与混淆**（`dr1003` → `445211101013`）。

```

```

### 1.7 返回码速查

| 响应                                                     | 含义                                     | 处理建议                                       |
|:------------------------------------------------- |:--------------------------------- |:--------------------------------------- |
| `{"result":1,"msg":"Portal协议认证成功！"}`              | 协议层成功                               | **仍需真实联网校验**（防伪登录）               |

| 大段 `<!DOCTYPE html …>`                                 | 接口形态不对                             | 多半打到了旧 :801 接口                         |

## 2. 是否有 HTTPS Portal

### 结论：**认证不走 HTTPS；但机器上确实开着 TLS 监听，用的是厂商默认测试证书。**

**① 配置层（权威）**：实时 `loadConfig` 返回：

| 字段            | 值       | 含义                             |
|:-------- |:---- |:------------------------- |
| `enable_https`  | **`0`**  | **门户未启用 HTTPS 认证**        |
| `ep_http_port`  | `801`    | 配置里的 HTTP 端口（实际用 803） |
| `ep_https_port` | `802`    | 配置里的 HTTPS 端口              |
| `domain_name`   | *（空）* | 没绑域名                         |

**② 端口实测**：

| 端口    | 明文 HTTP            | TLS 握手   |
|:--- |:------------- |:--- |
| `:801`  | ↪ HTTP 302（跳转页） | ❌ 失败     |
| `:802`  | ❌ 失败               | ✅ **成功** |
| `:803`  | ✅ HTTP 200           | ❌ 失败     |
| `:443`  | ❌ 失败               | ✅ **成功** |
| `:8443` | — 未开放 —           |            |

**③ 证书内容**：`:802` 与 `:443` 用的是同一张厂商默认证书：

```
C=CN, O=Doctorcom LTD., CN=demotest.doctorcom.com
```

即 **Dr.COM（Doctorcom）出厂自带的测试证书**，不是有效公网证书，任何客户端都要跳过证书校验才能用。

**④ 抓包侧**：5 份 HAR 共 **100 个请求，全部是 `http://`**，主机只出现 `10.0.10.252:803` 与 `10.0.10.252:801`。

### 实践建议

- **照 HTTP 实现即可**（这也是本项目的做法）。
- `:802`/`:443` 的 TLS 监听**不要依赖**：证书不可信、`enable_https=0` 说明校方并未启用，
  随时可能关闭；若要探测请务必禁用证书校验。

## 3. Portal 响应格式是否有变化

### 结论：**是 JSONP，不是纯 JSON；且并存三种包体形态。**

**① 主流形态：JSONP**

```
dr1001({"code":1,"msg":"加载页面设置信息成功!","data":{...}})
dr1002({"result":0,"msg":"获取用户在线信息数据为空！","list":[],"total":0})
dr1003({"result":0,"msg":"密码错误","ret_code":1})
dr1004({"result":1,"msg":"Portal协议认证成功！"})
```

- 形如 `drNNNN({...})`，`callback` 名由请求参数决定。
- ⚠️ **响应头 `Content-Type` 写的是 `text/html`**，不是 `application/json`。
  用 `Invoke-RestMethod` 之类会自动按 JSON 解析的库**会失败**：必须按文本取出后再剥离 JSONP 外壳
  （本项目就是用 `Invoke-WebRequest` 取原文 + 宽松正则解析）。

**② 错误形态：`code` 式**（**项目实测得到，本目录抓包里没有这条**：抓包时 key 都是对的）

```
dr0001({"code":403,"result":0,"msg":"请求参数包含非法内容，请检查后重试",
        "data":{"violations_count":1,"timestamp":"..."}})
```

注意这一条**同时含 `code` 与 `result`**：所以解析时不能只看 `result`。

**③ 非 JSONP：HTML 错误页**

旧 `:801 ?c=Portal&a=login` 接口与门户异常时会直接返回整页 HTML
（早年抓到的是 HTTP 500 + `系统发生错误`）。**判据：拿不到 `result`/`ret_code` 就当接口形态不对处理。**

**④ 包体字段差异（重要）**

| 接口           | 顶层字段                            |
|:------- |:---------------------------- |
| `loadConfig`   | `code` + `msg` + `data`             |
| `online_list`  | `result` + `msg` + `list` + `total` |
| `portal/login` | `result` + `msg` + `ret_code`       |

→ **三种接口的包体结构并不统一**，解析代码要分别处理或写得足够宽松。

**⑤ 全部出现过的响应 Content-Type**（5 份 HAR 统计）：
`text/html`（含接口 JSONP）、`application/javascript`、`text/javascript`、`text/css`、`image/png`、`image/jpeg`。

## 4. 是否有 IPv6 认证要求

### 结论：**当前没有。**

| 证据               | 内容                                                                                                   |
|:----------- |:----------------------------------------------------------------------------------------------- |
| **① 门户配置**     | 实时 `loadConfig` 返回 **`ipv6_state = 0`**（IPv6 功能关闭）                                           |
| **② 抓包请求参数** | 5 份 HAR 中所有认证相关请求的 **`wlan_user_ipv6=` 一律为空值**（每份 2~4 处）                          |
| **③ 主机侧**       | `Get-NetIPAddress -AddressFamily IPv6` → **无任何全局 IPv6 地址**，只有回环与链路本地                  |
| **④ 响应体**       | `loadConfig` 响应中 `ipv6` 字样仅 1 处（就是 `ipv6_state` 字段本身），无 IPv6 地址下发、无 v6 专属接口 |
| **⑤ 参数表**       | 认证参数集里没有任何 IPv6 形式的账号/IP 字段；`a79.htm` 入口页与 `wlanacip` 全是 IPv4                  |

### 但仍需知道

- 参数位是**预留好的**：`wlan_user_ipv6` 已存在于 loadConfig / online_list / login 三个接口，
  门户若将来开双栈，只需填这个字段：**届时 `ipv6_state` 会变成 `1`**。
- 本项目只实现了 IPv4（`Get-DrappallKey` 按 IPv4 字符串推导 XOR key）。
  如果将来 `ipv6_state` 变为 `1` 且认证改用 v6 地址，**key 推导与 `wlan_user_ip` 都要跟着改**。

## 5. 其他技术细节

### 5.1 GET 还是 POST

**全部是 GET。** 5 份 HAR 共 100 个请求，`GET=100 / POST=0`。

| 抓包                       | 请求数 | 方法   |
|:------------------- |:---- |:---- |
| `10.0.10.252-2.4G.har`     | 26     | 全 GET |
| `10.0.10.252-5G.har`       | 24     | 全 GET |
| `10.0.10.252-lan1.har`     | 22     | 全 GET |
| `10.0.10.252-lan2.har`     | 6      | 全 GET |
| `10.0.10.252-redacted.har` | 22     | 全 GET |

> ⚠️ 上表列出的 5 份抓包**已按隐私要求从仓库与本地全部删除**（它们含可还原的本机 MAC/IP）。
> 表中数字是当时的统计结果；要重新核对请按 [`captures/README.md`](captures/README.md) 自行抓取。

→ 连密码都是**放在 URL 查询串里**用 GET 传的（这就是为什么本文与项目文档都强调
「密码会进 URL，打日志前必须脱敏」）。

### 5.2 callback 计数机制

- 客户端内部从 `dr1000` 起自增。**实测两种走向**：
  - 完整会话（`-5G` / `-2.4G` / `-lan1` / `-redacted`）：`loadConfig=dr1001` → `online_list=dr1002` → `login=dr1003`；
    其中走过「先错后对」的 `-5G`/`-2.4G` 是 `dr1003`（`密码错误`）→ 重试 `dr1004`（成功）；
  - 一次就成的 `-lan1` / `-redacted`：`login=dr1003` 本身就是成功，**没有 `dr1004`**；
  - `-lan2` 只录了登录（6 条里 2 条登录、4 条资源），**不含 loadConfig / online_list**，同样能看到 `dr1003`（错误）→ `dr1004`（成功）这对。
- **同一个会话内 callback 是连续递增的**；服务端只负责回显，**不强校验具体值**
  （抓包里出现过 `415714151516`、`4d5b1819191a` 这类大值，同样正常返回）。
- callback 值**本身也参与 XOR 混淆**。

## 7. 如何自行复现这些结论

```powershell
# ① 端口 / TLS 探测：两项都真验：先 TCP，再分别试明文 HTTP 与裸 TLS 握手
#    （:443 / :802 用的是厂商默认证书，必须跳过证书校验才能握上手）
foreach ($p in 80,443,801,802,803,8443) {
    $tcp = New-Object Net.Sockets.TcpClient
    try {
        if (-not $tcp.ConnectAsync('10.0.10.252',$p).Wait(3000)) { ":$p 未开放"; continue }
        $line = ":$p TCP 开放"
        try { $null = Invoke-WebRequest "http://10.0.10.252:$p/" -TimeoutSec 5 -UseBasicParsing; $line += '；HTTP 可用' }
        catch { $line += '；HTTP 不可用' }
        try {
            $t2 = New-Object Net.Sockets.TcpClient; $t2.Connect('10.0.10.252',$p)
            $ssl = New-Object Net.Security.SslStream($t2.GetStream(), $false, { param($a,$b,$c,$d) $true })
            $ssl.AuthenticateAsClient('10.0.10.252')
            $line += '；TLS 成功，证书=' + $ssl.RemoteCertificate.Subject
            $ssl.Close(); $t2.Close()
        } catch { $line += '；TLS 失败' }
        $line
    } finally { $tcp.Close() }
}

# ② 实时拉取门户能力清单（HTTPS/IPv6 的权威回答都在这里）
$u = 'http://10.0.10.252:803/eportal/portal/page/loadConfig?callback=dr1001' +
     '&wlan_user_ip=MTAuMjAuMzAuNDA%3D&wlan_ac_ip=MTAuMTI4LjI1NS4xMjk%3D&jsVersion=4.X'
$t = (Invoke-WebRequest $u -UseBasicParsing).Content
$o = ($t -replace '^[^(]*\(','' -replace '\)\s*$','') | ConvertFrom-Json
$o.data | Select-Object enable_https, ep_http_port, ep_https_port, ipv6_state, visit_blacklist

# ③ 统计抓包里的 HTTP 方法（验证“全是 GET”）
Get-ChildItem .\captures\*.har | ForEach-Object {
    $h = Get-Content $_ -Raw -Encoding UTF8 | ConvertFrom-Json
    $g = @($h.log.entries) | Group-Object { $_.request.method }
    '{0}: {1}' -f $_.Name, (($g | ForEach-Object { "$($_.Name)=$($_.Count)" }) -join '  ')
}

# ④ 项目自带的登录联调（会打印已脱敏的登录 URL 与门户原始响应）
.\CampusNet_AutoLogin\CampusNet_Login.ps1 -TestLogin
```

## 8. 变化与风险提示

| 项                                  | 说明                                                                     |
|:---------------------------- |:----------------------------------------------------------------- |
| **`jsVersion` 会变**                | 实测登录用 `4.5.1`。门户升级后若变成别的值，旧请求可能被拒：**先查这里** |
| **AC IP 会变**                      | 有线/无线走不同 AC（`10.128.255.129` vs `10.129.255.248`），**不可写死** |
| **XOR key 随 IP 变**                | 由本机 IP 推导，换网段必须重算，否则 `dr0001 code=403`                   |
| **`:802`/`:443` 的 TLS 不保证可用** | 厂商默认证书 + `enable_https=0`，随时可能关闭                            |
| **IPv6 可能将来启用**               | `ipv6_state` 一旦变 `1`，认证参数与 key 推导都要复核                     |
| **密码走 GET 明文**                 | 密码在 URL 里，**日志/截图/分享链接都要脱敏**；建议定期改密码            |
| **不要拿 blacklist 里的地址做探针** | 门户不劫持它们，探测永远得不到重定向                                     |

## 10. 认证机制总览（2026-10 实测补充）

> 本节证据来自三处：**门户自带 JS**（`raw/a40.js`、`raw/a41.js`）、**实时 `loadConfig` 响应**、**真机端口探测**。每条都标了出处，没实测的一律标"未验证"。

### 10.1 端口分工（已定案 · 真机实测）

| 端口    | HTTP    | HTTPS   | 用途                   |
|:--- |:--- |:--- |:--------------- |
| 801     | 302     | 000     | 旧 HTTP 入口（会跳转） |
| 802     | 400     | 302     | 纯 HTTPS 跳转口        |
| **803** | **200** | 000     | **真实 eportal API**   |
| 804     | 400     | **200** | HTTPS 服务口           |

- 与门户 JS `a41.js:5-11` 声明的 `epHTTPPort=803` / `enHTTPSPort=804` **完全一致**；
- `loadConfig` 返回的 `ep_http_port=801` / `ep_https_port=802` 指的是**旧/前端**端口；
- **结论：调接口一律用 803。**

### 10.2 认证相关的实时开关值（2026-10 拉取）

| 字段                             | 值        | 含义                                                                       |
|:------------------------- |:----- |:------------------------------------------------------------------- |

### 10.3 多设备在线机制

- 上限与判定**在 RADIUS 侧**（`find_mac=0` + `check_online_method=1`，2026-10 实测）；
- 超额时后端返回 **`over_mac_list`**，前端弹「账号已超出最大登录数」并**列出设备供手动下线/解绑**（`a40.js:2282-2286`、`6913`）；
- 解绑接口 `mac/unbind`、`login_verify/unbind`（`a40.js:2730-2738`、`6944-6952`）；
- **门户 JS 里没有任何"后登录踢先登录"的分支**（grep `踢|replaced|已经在线` 仅命中 `ret_code=2`），因此**是否互踢由服务端配置决定，只能实测**；
- 现网观察：上限 **2 台**（PC + 手机），此值为现场经验，**未在源码中找到数值**。

### 10.4 门户返回码权威表（`a40.js:1560-1604` 原文）

| `ret_code` | 门户原文含义              |
|:--- |:------------------ |
| 1 / 4      | 账号 / 密码类错误         |
| 2          | 终端IP已经在线            |
| 3          | 系统繁忙                  |
| 5 / 6      | REQ_CHALLENGE 失败 / 超时 |
| **7**      | **Radius认证失败**        |
| **8**      | **Radius认证超时**        |
| 9 / 10     | Radius 下线失败 / 超时    |
| 11         | 其他错误                  |
| 998        | Portal 协议参数不全       |

> ⚠️ **更正**：本仓库早期文档把 `ret_code=8` 记作「IP/MAC 不匹配」（错记），与门户 JS 原文（「Radius认证超时」）**不符**，本表为准。
> 💡 若认证界面弹「radius 认证失败」，对应的是 **`ret_code=7`**，属 **AC ↔ RADIUS 报文/超时**问题，与密码错（1/4）、已在线（2）不是一回事。

### 10.6 真机运行记录（2026-10-10、10-12）

> 三次运行：`-Diagnose` 两次（当日两次）、`-TestLogin` 一次（当日）。当时网卡状态：有线 `Up` 且有网关；`WLAN` 为 `Disconnected`（残留 APIPA 地址）。**按脱敏约定，本节不记录真实 IP/MAC**。

| 观察项                                         | 实测结果                                                  | 结论                                                            |
|:--------------------------------------- |:-------------------------------------------------- |:-------------------------------------------------------- |
| 登录请求是否被门户接受                         | 返回 `dr1003({"result":0,"msg":"AC999","ret_code":2})`    | **通**。接口、参数、XOR 混淆全部被门户认可                      |
| `ret_code=2` 的真实含义                        | 同一时刻「真实联网校验 = **True**」                       | 就是**本机（本终端 IP）已在网**，与"账号在别处登录"无关         |
| `loadConfig` 的 `program_index` / `page_index` | 两次拉取（相隔约 40 分钟）**完全相同**，`page_name=gzlg1` | 该值长期稳定；脚本仍每次现拉，不依赖这一点                      |
| 门户探针 `9.9.9.9`                             | **无响应**（约 6 秒超时后被丢弃）                         | 本校园网**不放行**该地址；脚本会继续试下一个，但每次白花约 6 秒 |
| 门户探针 `www.baidu.com` / `www.qq.com`        | HTTP 200 / HTTP 302（跳自身 HTTPS 站）                    | 两个探针均正常，且**都未出现门户跳转**（已联网时的正确表现）    |
| `WLAN`（未连接）                               | 状态 `Disconnected`、IP 为 `169.254.x.x`、无网关          | 诊断如实标为「不可用」并给出原因，**没有**误判成"需要修复"      |
| `-TestLogin` 的脱敏                            | 账号、密码字段均显示为 `***`                              | 脱敏有效，登录 URL 可以安全外发                                 |

**由本次记录得出的两条实践结论**：

1. **`ret_code=2` 应当读作"本机已经在线"**：此时的正确处理是「无需重复登录」，而不是提示用户去下线别的设备；
2. **无线侧 AC 地址已取得（两次一致，见 10.6.1）；登录请求仍未实跑**：三次运行期间 `WLAN` 始终是 `Disconnected`，所以 `wlan_ac_ip`、无线侧 IP/MAC 与 key 都**还没有实测数据**，仍需在真正连上校园 WiFi 后再跑一次（见《待排查清单》）。

#### 10.6.2 无线侧 AC 地址与拔插场景（2026-10-10 上午）

**① 无线与有线走的是不同 AC（已实测）**

| 接入方式 | `wlan_ac_ip` | 来源 |
|:-------- |:------------ |:---- |
| 有线 | `10.128.255.129` | 历史抓包与实测 |
| **无线（5G 与 2.4G 相同）** | **`10.129.255.248`** | 未认证时门户跳转 URL 里的 `wlanacip` 参数 |

- **只能从门户跳转里读到**：探针被劫持时返回的 HTML 内含 `location.href="http://10.0.10.252/a79.htm?wlanusermac=…&wlanuserip=…&wlanacip=…"`，AC 地址就在这条 URL 上；`loadConfig` 读不到它。
- 两个 SSID（5G 与 2.4G）拿到的是**同一个** AC，且客户端 IP 也相同 → 同一网段、同一 DHCP 作用域。
- 实践含义：**AC 地址不能写死**，脚本按当前网卡推导 key 的做法是对的。

**② 同一探针在两种状态下表现相反（重要）**

| 机器状态 | `http://9.9.9.9/` 的表现 | 原因 |
|:-------- |:------------------------ |:---- |
| **未认证** | **HTTP 200**，且返回体是**门户的重定向 HTML** | 包被门户拦下并伪造响应 |
| **已认证** | **无响应**（超时） | 请求直达真实 9.9.9.9，而该地址在本校园网不回包 |

- 结论一：**200 不代表“能用”**：未认证时也能拿到 200，这正是「伪登录」的判定难点，所以必须做 HTTPS 内容校验。
- 结论二：**探针列表宜把 `9.9.9.9` 降为兜底**：它在已认证状态下必然超时，每次白等约 6 秒。

**③ “拔插网线后不跳转认证”的分阶段解释**

| 阶段 | 现象 | 性质 |
|:---- |:---- |:---- |
| 刚拔插的几秒～几十秒 | 网卡仍为 `Disconnected`（链路没起来），脚本报“没有选出可用网卡” | **正常**：链路与 DHCP 租约需要时间就绪，稍等重跑即可 |
| 链路起来后 | 直接 `互联网连通: True`，无需重新认证 | **正常**：会话在服务端仍存活（同一 MAC），拔插不断会话 |
| 全程 | **Windows 从不弹“登录到网络”提示** | **正常**：Windows 用的探测域名（`www.msftncsi.com` 等）**恰好都在门户的 `visit_blacklist` 里不被劫持**，所以它永远看不到 captive portal：这也是必须靠本脚本主动探测的原因 |

> 本次据此修掉一个**提示与事实不符**的小缺陷：此前“没有可用网卡”时会**无条件**打印“网卡只有 169.254.x.x（APIPA）”，而实际两张卡都是 `Disconnected` 且带着残留的真 IP。现在改为按事实分支：真有 APIPA 才提示 APIPA，否则提示“网卡都没有链路，刚拔插过需要等几秒到几十秒”。

**④ 补充：拔插后链路「始终起不来」的情形（2026-10-10 实查）**

前面③说的是正常情况（等几秒就好）。但还有一种**物理层**情形，值得单独记下来：本次实测遇到：

```
以太网  Intel(R) Ethernet Connection (19) I219-V
        Status = Disconnected
        MediaConnectionState = Disconnected   ← 物理链路没建立
        LinkSpeed = 0 bps                     ← 端口协商不到速率
        AdminStatus = Up                      ← 设备没有被禁用
```

判断要点：**`LinkSpeed = 0 bps` 表示网卡连“线插上了”都没感知到**，此时：

- **与门户、认证、脚本都无关**：问题在链路层之下，登录逻辑根本走不到；
- **脚本的诊断是对的**：它会如实写出「链路未连接（Disconnected）：网线没插好 / 对端口没通电」；
- ✅ **`-Repair` 现已支持这种卡**（2026-10-10 增强）：`Get-CampusRepairPlan` 仍然只负责「链路 `Up` 却拿不到有效 IP」的网卡（那类走 Release/Renew）；新增的 `Get-CampusLinkDownAdapters` 会挑出「**非虚拟 + `Disconnected` + 仍带残留 IPv4**」的卡（有残留租约才说明它曾经拿过地址，多半是驱动卡住，而不是压根没插线），以管理员身份运行 `-Repair` 时会对它们执行 `Restart-NetAdapter`（等价于设备管理器里禁用→启用）。非管理员时会明确提示需要提权。

**可行的处置顺序**（从便宜到麻烦）：

1. **换网线 / 换墙上的端口**：`LinkSpeed = 0 bps` 常见于线缆或对端口问题；
2. **设备管理器里把网卡「禁用」再「启用」**：等价于重新初始化驱动，**不必重启电脑**；
3. **管理员权限**执行（用网卡描述而不是中文别名，避免编码问题）：
   ```
   Restart-NetAdapter -InterfaceDescription 'Intel(R) Ethernet Connection (19) I219-V'
   ```
   这一步**需要管理员**；普通权限会话跑不了（本次实测当前会话 `IsInRole(Administrator)` 为 `False`）。

**由 10.6.3 得出的三条结论**：

1. **无线侧全链路可用**：从门户发现（拿到无线 AC 地址）到发起登录、再到真实联网校验，全部走通；有线与无线**各自的 AC 地址确实不同**，且脚本按当前网卡 IP 现算 XOR key，无需为无线做任何额外配置。
2. **协议实现与 HTTP 客户端无关**：PowerShell 与 `curl.exe` 两条通道都能拿到 `result:1`，说明参数拼装与混淆算法本身是正确的，排障时可用 `CampusNet_CurlTest.ps1` 快速区分「协议问题」与「脚本问题」。
3. **「拔插网线不跳转」有明确分层**：若 `LinkSpeed = 0 bps`，问题在**物理层**——`-Repair` 的重启网卡只能排除驱动侧，救不回线缆/端口问题；此时应先换线、换口。

### 10.7 多设备与共享检测：能证实什么、不能证实什么

> **前提**：多设备判定发生在 **AC / RADIUS 网络侧**，门户页面里的 JS 是**客户端代码**。所以"翻门户源码"既**不能证明**也**不能否证** TTL、IPv4 Identification、DPI、时钟偏移这类网络层手段：它们在 JS 里**本来就不可能出现**（本仓库 `raw/` 五个文件里 `ttl` / `ip_id` / `identification` / `ip_header` / `src_ip` / `dst_ip` 命中数**全为 0**）。

#### 10.7.1 有三类结论，别混为一谈

| 结论类型               | 含义                                                   | 例子                                                                  |
|:--------------- |:----------------------------------------------- |:-------------------------------------------------------------- |
| **不可能存在**         | 技术上已被淘汰，或不适用于本场景                       | Flash Cookie（Flash Player 已于 2020 年底全面 EOL）                   |
| **采集确凿、用途未知** | 源码证明它**确实被上传**，但"是否用于多设备判定"无证据 | `User-Agent`（`a40.js:2200` `data.user_agent = navigator.userAgent`） |
| **源码不可判**         | 判定在网络侧，客户端看不见                             | TTL、IPv4 Identification、DPI、协议栈时钟偏移                         |

#### 10.7.2 有硬证据的两条实际机制

社区对 Dr.COM 官方客户端的逆向整理（[drcom-generic / analyses/error_no.md](https://github.com/drcoms/drcom-generic/blob/master/analyses/error_no.md)）给出了服务端**确实会下发**的判定：

| 错误码          | 门户原文含义                                   |
|:-------- |:--------------------------------------- |
| `0x07`          | IP 地址不匹配（账号只能在指定 IP 使用）        |
| `0x0B` / `0x16` | MAC 地址不匹配（账号只能在指定 MAC + IP 使用） |
| **`0x14`**      | **「本帐IP地址太多」：多设备上限的直接体现**  |
| `0x17`          | 客户端设置了静态 IP，请改为动态获取（DHCP）  |

与本校园网实测吻合：`check_online_method=1` + `find_mac=0`（在线检查与 MAC 列表均走 RADIUS）、门户 JS 的 `over_mac_list` → `show_unbind_box()`（超限时弹框让用户手动解绑）。

**结论：多设备判定 = 服务端按「账号 → IP 集合 / MAC 集合」计数**，与 TTL、IPv4 ID、时钟偏移**无关**。

#### 10.7.3 厂商侧可核实的部分

Dr.COM 官方产品页 [APG 防代理网关](https://www.drcom.com.cn/productdetail/BRK1lMEN) 明确写了这一能力：网络行为分析、实时分析用户网络应用数据报文进行识别、提供特征库更新以识别新型代理接入、支持"终端类型与拖带数量"的组合策略。

两点必须说清：① 官方文案**没有出现 DPI、TTL、IP-ID、时钟偏移、Flash 等任何具体字段名**，只说"行为分析 + 特征库"；② 这属于 **APG 产品线**，**不等于**本校基础认证网关就开着该能力。
